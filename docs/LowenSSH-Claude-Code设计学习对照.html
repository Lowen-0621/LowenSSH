借鉴原则，重写实现。

LowenSSH 从 Claude Code 学到的核心，不是某几个正则或某段提示词，而是： Agent 的安全必须由模型外部的宿主程序裁决；长对话必须分层减重，而不是等到上下文溢出再处理。

资料边界：本手册不保存、不镜像、不复现 Claude Code 泄漏源码，只依据 Anthropic 官方文档、 针对公开版本的学术架构分析与泄漏事件报道做机制级对照；LowenSSH 部分全部来自本地可验证源码。

一句话定性

Claude Code 提供了设计参照；LowenSSH 完成了面向 SSH 运维场景的简化重实现。

02 / Security

安全策略：模型提出，宿主裁决

这是 LowenSSH 学习 Claude Code 最清晰的部分。关键并不是“列一个危险命令黑名单”，而是把模型从授权链中移出去， 让它无法凭自己的输出绕过安全检查。

Claude Code · 机制抽象

PUBLIC ARCHITECTURE
模型生成 tool request
宿主层预过滤与权限规则匹配
更严格规则优先：deny / ask / allow
必要时用户确认、hooks 与 sandbox
执行或返回 blocked reason
模型根据拒绝原因改用安全方案

LowenSSH · 实际链路

LOCAL SOURCE
关闭 Spring AI 自动工具执行
解析 execCommand.command
CommandGuard 拆分复合命令
DENY 直接拦截 / ASK 交确认器
ALLOW 或已确认命令才执行并审计
拒绝结果按 tool_call ID 回灌，继续循环
CommandGuard.java · 核心裁决 打开源码 ↗ 
public enum Decision { DENY, ASK, ALLOW }

public Verdict evaluate(String command) {
  for (String seg : splitSegments(command)) {
    Verdict verdict = evaluateSingle(seg);
    // 取最严结果：DENY > ASK > ALLOW
  }
}

private Verdict evaluateSingle(String segment) {
  for (Pattern p : DENY) { /* 命中即拒绝 */ }
  for (Pattern p : ASK)  { /* 交给确认器 */ }
  return new Verdict(ALLOW, "");
}

这里真正学到了什么？

  • 授权外置：Prompt 只能提醒模型，不能成为硬安全边界。
  • Deny 优先：同一命令同时命中多条规则时，最严格结果获胜。
  • 检查实际参数：不判断模型“说得像不像安全”，只看将要执行的命令。
  • 拒绝可恢复：门禁不是简单报错，而是给 Agent 一个可继续推理的反馈。

LowenSSH 自己的落地价值

  • 把 Spring AI 原本可能自动执行的阶段显式拆开。
  • 针对 SSH 场景补充 find -delete 等真机联调中出现的等价绕过。
  • 被阻止命令进入审计日志，便于复盘模型为什么被拦。
  • Java、CLI TypeScript、Flutter Dart 三端都有同类门禁实现。
03 / Context

上下文策略：先削大块，再压旧历史

SSH 命令经常返回几 KB 到几十 KB 的日志。若每一轮都把全部工具结果重新发给模型，Agentic Loop 的输入会快速膨胀。 LowenSSH 没有照搬完整层级，而是选了收益最高、最适合运维的两层。

STEP 01

工具结果预算化

Claude Code：先削减占用最大的工具输出。LowenSSH：分级截断中段，保留日志头尾，完整结果落库。

为什么适合 SSH？

  • 日志头部常包含命令、时间和上下文；尾部常包含最新错误或汇总结论。
  • 最近消息保留更多细节，旧消息收紧到更小预算。
  • 只压缩“回灌模型的副本”，完整工具输出仍在 t_message 中可追溯。
  • 截断标记保证幂等，避免每轮改写历史破坏 GLM 前缀缓存。

摘要保留什么？

  • 用户原始运维目标。
  • 关键命令及结果结论，而不是冗长原始输出。
  • 已发现的问题和系统状态。
  • 被门禁拦截的危险操作。
  • system 与最近 K 条消息保持原文；摘要连续失败 3 次后熔断。

04 / Boundaries

必须主动说清的差距

诚实说明边界不会削弱项目，反而能证明你真正理解了产品级 Agent 安全与个人项目之间的距离。

01

默认策略不同

LowenSSH 未命中规则时默认 ALLOW；Claude Code 的公开设计更强调未授权动作升级询问或失败关闭。两者安全强度不等价。

02

Web 端 ASK 自动批准

AgentController 使用 AutoConfirmationHandler，因此 ASK 在 Web 入口没有真正的人在回路；只有 DENY 仍是硬阻断。

03

正则不是 Shell 解析器

变量展开、$()、反引号、别名、脚本文件和编码绕过都可能逃出简单正则。CLI 已补了整句 fork bomb 检查，但 Java 版仍存在同步缺口。

04

没有同等级沙箱

LowenSSH 的核心边界是命令门禁与审计，没有 Claude Code 那样完整的文件边界、沙箱、hooks 与多层权限管线。

05

压缩层级是主动精简

只实现工具输出截断和历史摘要，没有实现 snip、microcompact、context collapse 等层，不能表述为“复现 Claude Code 上下文系统”。

06

Token 估算较粗

运行时以 字符数 / 2.5 估算 token，简单、低依赖，但不如模型 tokenizer 或 API usage 精确。

07

幂等与进一步收紧的取舍

工具结果一旦带截断标记，进入旧区后不会按更小阈值二次截断；代码选择缓存前缀稳定，而不是继续节省几百字符。

06 / Interview

面试时应该怎么讲

不要说“我复刻了 Claude Code”，也不建议沿用源码注释里的“抄”。最准确的表述是“参考其公开设计原则，结合 SSH 场景做了简化重实现”。

30 秒版本

LowenSSH 的安全和上下文管理参考了 Claude Code 被公开分析后的宿主层设计。安全上，我没有让模型自我约束，而是关闭 Spring AI 的自动工具执行，在代码层加入 deny、ask、allow 三态门禁，拒绝原因会回灌给模型继续寻找安全方案。上下文上，我选择了最适合 SSH 的两层：先分级截断大工具输出，再在超过预算时摘要旧历史。它是结合 Spring AI 和运维场景的简化重实现，不是对 Claude Code 的完整复刻。

深挖版本

我主要学习了两个原则。第一，模型负责决策但不能负责授权，所以我关掉框架自动执行，将 execCommand 的实际参数送入独立 CommandGuard，deny 直接拦、ask 由确认器处理、allow 才执行；拦截结果保持 tool_call 配对后重新送回模型。第二，上下文要渐进减重。我对最近与较早的工具结果使用不同阈值，超长日志只留头尾且完整内容落库；整体超过阈值后，再用 LLM 摘要旧历史，并保护 tool_call 与 tool_result 配对，摘要连续失败会熔断。当前差距也很明确：正则门禁不是完整 Shell 解析器，Web 端 ASK 还会自动批准，也没有 Claude Code 同等级的沙箱和全部压缩层级。
